# Ansich v1 分阶段实施计划

本目录把 [Ansich v0.2 设计](../ansich-design-document.md) 拆成十二个可独立执行、可独立验收的阶段。阶段按顺序交付，每个阶段都必须形成一条可运行的纵向切片，而不是只提交数据表、只提交探针或只提交页面。

- **Phase 11-A 采集与写入韧性（2026-08-20，`246964e5`..`31dc9907`，含批内基线卫生修复 HOTFIX-0 `ae731b18`）**：Phase 11 拆成三批交付，这是第一批，范围严格是 [11-resilience-replay-and-retention.md](11-resilience-replay-and-retention.md) 的 **§2（Collector 与 BatchWriter 加固）加上 F10-7**；§3/§4/§9 归 B 批，§5–§8 归 C 批，本批一条都没碰。零迁移，head 仍是 `0026_ansich_environment`。落地的语义：
  - **生命周期**：`derive_status` 是对当前事实的**纯函数**（无记忆、不保存状态，因此不会与它所描述的服务失步），状态从四个扩到七个（新增 `starting`/`recovering`/`shutting_down`）。钳制集 `LEGAL_TRANSITIONS` 比 §2 的示意图**更宽**：§2 的八条边是标称弧，作为**被钉住的子集**保留（`backend/tests/ansich/test_lifecycle.py::SPEC_SECTION_2_EDGES`），钳制集则是这套推导真正可达的闭包（17 条边，每条都在模块里写了一行可达性理由，覆盖运维恢复、任意运行态下的 stop、start 之后的第一次读，以及重启）。**把钳制集放宽到闭包是一处显式记录的 spec 偏离**——照着示意图钳制会在正常运行中翻红；必须保持非法的那一半由否定式序列钉住。`recovering` 必须有**事故证据**（未上报的丢失范围，或 writer 的重试积压），**绝不**由裸队列深度推出：一次负载高峰不是事故，拿它当证据会凭空造出 §2 图里没有的 `healthy -> recovering`。另加 start/stop 的重入守卫。
  - **per-producer 账目**：每个 `(producer, instance)` 一行 accepted/dropped/last-seq/序列化失败/最后一次成功 flush，LRU 上界 256。措辞纪律：`evicted_producer_count` 数的是**驱逐事件**，不是被驱逐的 producer 数。
  - **writer**：被拒的批次先做有界指数退避重试（100ms 起翻倍、上限 5s、至多 5 次），**等待期间不持任何锁**（`persist_lock` 只覆盖出队加第一次尝试；因此 terminal barrier 可以越过一个**正在等待**的 writer，但绝不会越过一个**正在写**的 writer——ingest 序与 collector 序分叉是本系统既有的晚到形状，watermark 加宽正是为它存在的）。批次预算耗尽后逐条隔离（`writer_item_max_attempts`），一条毒行只赔它自己，reason 为 `poison_observation`；`poison_observation_count` 分不清「真毒行」与「拖过全部预算的总体故障」。**一次总体故障拖过全部预算时，队列会以有界速率排空成丢失**——这是 v1 没有 spool/WAL 的既定代价，进程崩溃前未 flush 的数据仍是明确的 known limitation。另一处诚实的不对称：提交落库之后才到达的取消会把一个 durable 批次整批记成丢失（幻影丢失），方向是**宁可多报**、且是进程本地的。
  - **terminal barrier**：以 **collector sequence** 为界（按序排空所有 ≤ S 的排队项），**超时不再丢弃**——没能落库的行退回**队列头**，由 writer 在存储恢复后写入（与旧的丢弃语义相反）；barrier 自己取走的选择集会登记进 in-flight，因此 `in_flight_count` 的含义是**全部在途行**，包含 barrier 的写。`FlushResult` 新增 `{persisted_through, lost_ranges, timed_out}`。措辞纪律：`persisted_through` 是**连续**已持久化的最高 collector 序号，因此**任何一次丢失之后它就退化为首次事故前的前缀**并停在那里——这是刻意选的语义（宁可少报，不可多报），必须与 `lost_ranges` 配对读才是完整图景。
  - **进程级丢失范围**：`observability.degraded` 以丢失范围的 Task 为 subject，所以 `task_id=None` 的进程级范围**根本写不出去**。它们被放进一个显式的未上报桶，以 health 字段 `unreported_global_lost_range_count` 呈现，并且**只要没被写出去就绝不标记为已上报**。**进程级范围的账目已经诚实，持久化留待 B 批的 host-`Scope` subject 设计**。
  - **回执（F10-7 结清）**：改为按 observation 所处**状态**解析的四级阶梯（在队列里或在 writer 手上 → `pending`；已被记为丢失 → `failed`；已落库 → 由它自己的 projection job 决定，而 accepted 却无 job 读作 `failed`；三处都不在 → `failed`，推定丢失）。连带修正了反向的一半：barrier 超时现在读作 `pending`，因为那一行还活着。末档「三处都不在即丢失」的前提是 **id 归本进程所有**（单 collector），已写进 docstring。
  - **停机**：`stop_drain_timeout_ms` 通过取消来界定**这次尝试本身**（一个永不返回的 persist 会被取消），而不只是界定排队量或重试次数，所以卡死的存储调用**扛不住** shutdown——但这只对 **writer** 成立，projector join 仍是无界的（§8 的完整关闭顺序归 C 批）。预算耗尽时余下的行被记为丢失并发一条不受限速的 WARNING；**预算内完成的排空即使记了丢失也只体现在计数器上、不发任何警告**，这是一处运维可见性缺口，读「安静的停机」时必须知道。
  - **丢失上报**：coalescing 不再静默延长一条已上报的范围（延长部分自己开一条、自己被上报）；合成的 `ansich-collector` 上报者仍然把 collector 序号写进 `producer_seq`，这是最后一处混用两个编号空间的地方。
  - **配置**：新增五个 startup-only knob（`writer_retry_max_attempts` 5、`writer_backoff_initial_ms` 100、`writer_backoff_max_ms` 5000、`writer_item_max_attempts` 2、`stop_drain_timeout_ms` 10000），已同步 `config.example.yaml`（`config_version` 33→34）；本批同时把整个 `ansich` 段的字段描述统一补上 `startup-only:` 前缀（纯描述，零行为）。前端七态端到端支持，`starting`/`shutting_down` 渲染为**静默的阶段行**而不是绿色的「数据健康」。
  - **HOTFIX-0**（`ae731b18`）：`budget_health` 的两个生产写者共用同一个纯函数 `order_wall_time_evidence` 收敛证据序（时钟无关性已用 2026/2099 双 fixture 证明）；该危害的**断言结构形状**那一半登记为 F10-24，归 B 批。

## 固定实现边界

以下决策适用于全部阶段，若实现中需要改变，必须先修订设计文档和受影响的阶段计划：

1. `backend/packages/ansich/` 是独立 Python 包，放置 Observation、Entity、Belief、Relation 等领域契约，以及不依赖 DeerFlow、LangGraph、FastAPI 的投影和查询逻辑。
2. `backend/packages/harness/deerflow/ansich/` 是 DeerFlow 适配层，放置 SQLAlchemy 表、仓储、Gateway 进程内服务装配和运行时探针。依赖方向只能是 `deerflow -> ansich`。
3. `backend/app/gateway/routers/ansich.py` 只做认证、请求校验、DTO 转换和调用应用服务，不在路由中写投影或规则逻辑。
4. `frontend/src/core/ansich/` 负责 API 类型、TanStack Query hooks 和纯转换函数；`frontend/src/app/workspace/ansich/` 与 `frontend/src/components/workspace/ansich/` 负责页面和组件。
5. Ansich 与 DeerFlow 共用已配置的 SQLAlchemy Engine/SessionFactory，但只写 `ansich_*` 表，不修改 `run_events` 语义。
6. 所有采集失败均 fail-open；现有 Token、循环、授权、超时等 DeerFlow 执行保护仍在本地同步路径中 fail-safe。
7. 除 Observation/Payload 外，Entity、Belief、Relation、Usage 和 Read Model 都是可删除、可按 projector version 重放的投影。
8. 后端实现强制 TDD。每个阶段先提交失败测试，再实现；SQLite 和 PostgreSQL 语义都要覆盖。前端新增行为必须有 unit test，关键操作流必须有 Playwright E2E。

## 阶段合并规则

每个阶段完成时必须同时满足：

- 迁移可在空 SQLite、已有 SQLite、空 PostgreSQL、已有 PostgreSQL 上执行；降级策略有明确说明。
- 新增 Observation kind 有 schema version、幂等 source event ID 生成规则和至少一个重复/乱序测试。

- UI 显示投影时间、丢失范围或 `unknown`/`unassessed`，不把资料缺失展示成健康或零值。
- 失败注入证明 Ansich 不改变 DeerFlow Run 的业务结果。
- 相关 README、`backend/AGENTS.md`、`frontend/AGENTS.md` 与配置示例同步更新。
- 新增或改变领域概念时同步更新 [../concepts.md](../concepts.md)（human-followups D1 的配套动作，防止概念导览再次腐化）。
